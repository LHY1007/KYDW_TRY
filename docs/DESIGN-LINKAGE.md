# KYDW 页面设计与联动说明

更新日期：2026-08-11

本文件记录 KYDW_TRY 的页面、合集、区块、数据源和教学材料之间的关系。它面向后续维护者，不属于网站正文。修改一个页面或数据对象前，先判断它是否被其他页面复用，再决定是更新唯一数据源、增加一个上下文显示规则，还是只做局部页面调整。

## 1. 维护时先记住的三条关系

1. `content.js` 保存团队、活动、项目、资源和页面文案；`site.js` 负责把这些数据组合成页面；`styles.css` 负责共享视觉规则。优先改数据，不在页面模板中复制同一段正文。
2. 同一内容可以有多个阅读入口，但入口职责不同。例如，项目详情页负责说明项目并引导读者进入材料，实践页负责说明如何运行实践，实践项目参考答案页负责展示代码、说明和结果。不要把三个入口合并成一个混杂页面。
3. 首页是摘要和入口，合集页是目录，详情页是完整说明，材料页是实际学习内容。修改上游内容时，沿着这条路径检查下游页面；没有受影响的页面不加入本次验收。

## 3. 页面、合集和区块的职责

### 3.1 首页 `index.html`

首页只回答“KYDW 是什么、现在有哪些值得进入的内容、从哪里开始”。

| 区块 | 作用 | 内容来源 | 修改时检查 |
| --- | --- | --- | --- |
| 首屏 | 建立团队身份，给出团队介绍、项目与活动、资源中心三个主入口 | `team.lead`、`team.paragraphs` | 团队介绍页首屏和首页首屏是否仍然一致 |
| 团队概况 | 用较短的视图展示成员高校、负责人、代表性成果和团队近期动态 | `team` | 团队页、负责人页、成果页、动态页 |
| 成员高校 | 自上而下展示直博、国内学硕/海外研究型硕士、在校本科生成员高校；学校标签横向换行 | `team.destinationRecords`、`team.destinationUniversityOrder`、`team.undergraduateNetwork` | 成员去向页和团队介绍页；不在模板中另写学校名单 |
| 负责人 | 展示负责人摘要，点击后进入 `team/people.html` 对应条目，不在首页展开完整履历 | `team.leaders` | 负责人子页面锚点、姓名、年级和简介 |
| 代表性成果 | 展示成果分类摘要，并为团队近期动态留出连续浏览空间 | `team.achievementMetrics`、`team.achievementNote`、`team.news` | 完整成果页、动态页；数字和详细条目不能只改一处 |
| 项目与活动 | 突出当前本科生科研入门体验项目；环境准备可直接进入，其他项目先显示项目预览并进入项目主页详情 | `experience`、`projects`、`modules` | 项目总览、Week 页面、项目详情和开放状态 |
| 人员招募 | 接收论文研究项目与科研实习项目发布群；体验项目和科研与实践活动不进入 | `recruitment.records` | 招募合集、详情页、状态筛选和发布群二维码 |
| 资源中心 | 只显示三个同层级合集的用途和入口，不把单个专业或单个材料提升为顶层栏目 | `resourceCollections` | 资源中心目录及各专题页 |
| 联系我们 | 为团队和体验项目提供公开联系方式；同一组二维码在不同页面可以使用不同标题 | `experience.contact` + `contactMarkup` 上下文参数 | 首页和体验项目主页，图片路径、邮箱和标题 |

首页不承担完整论文说明、完整履历、完整教学正文或所有项目材料。需要详细阅读时，页面应指向相应合集或详情页。

### 3.2 团队介绍

`team/index.html` 是团队信息的完整入口。它可以复用首页的数据，但不复制首页模板中的摘要文案。

| 页面 | 职责 | 复用数据 |
| --- | --- | --- |
| `team/index.html` | 团队定位、概况、成员高校、工作方式、成果摘要、成员发展、活动体系和负责人入口 | `team.*` |
| `team/news.html` | 展示与首页相同的完整团队近期动态；首页是浏览区，本页是详细列表 | `team.news` |
| `team/achievements.html` | 展示团队近期动态和代表性成果的完整内容 | `team.news`、`team.achievements` |
| `team/destinations.html` | 以学位组和具体记录展示毕业成员去向，并补充在校本科生高校网络 | `team.destinationRecords`、`team.undergraduateNetwork` |
| `team/activities.html` | 展示活动目录和团队活动说明 | `modules`、`team.activities` |
| `team/people.html` | 展示负责人和历届骨干的完整介绍，首页点击后通过锚点进入对应人员 | `team.leaders` |

负责人简介的摘要、详细段落、姓名和职务只维护在 `team.leaders`。新增或修改履历时，首页只显示摘要，负责人页显示完整段落；不在 `site.js` 写第二份人物介绍。

### 3.3 项目与活动合集

`programs/index.html` 是活动目录，不是某一个项目的教学正文。当前顺序为：本科生科研入门体验项目、科研技能入门与查缺补漏、KYDW科研入门培训、课程项目、专题交流。新增活动只需在 `modules` 或体验项目数据中登记，并指定排序、状态和详情页。

各类活动详情页的职责如下：

- `programs/research-skills.html`：长期科研技能参考入口；十二个章节由 `programs/research-skills/*.html` 承载。
- `programs/training.html`：说明 KYDW科研入门培训的活动范围、阶段任务和培训路径；长期知识链接科研技能项目。
- `programs/sdu.html`：说明山东大学本科生暑期名校课程-神经影像学与人工智能的定位、日期、受众和课程目录；每一节进入对应 `programs/sdu-lesson-*.html`，子页面再提供实际 Kaggle 实践入口。
- `programs/fudan.html`：说明复旦大学秋季学期本科生践悟课程及授课内容；课程完成状态和课程标题从 `modules` 的课程数据读取。
- `programs/workshop.html`：说明生物医学人工智能专题交流，不与专业解读或科研体验项目重复。

课程名称、日期、授课标题、受众和 Kaggle 入口属于课程数据；不要在首页卡片、课程详情页和子页面分别手写三套版本。

### 3.4 人员招募

`recruitment/index.html` 从 `recruitment.records` 生成论文研究项目和科研实习项目发布群记录。记录状态只使用“进行中、即将开始、已结束”。发布群详情读取 `recruitment.contact.internshipGroupQr`，该字段与首页、体验项目联系区域共用 `assets/contact/project-announcement-qr-cropped.png`；替换这一图片文件后，所有引用页面同步更新。

### 3.4 本科生科研入门体验项目

体验项目是一个可扩展的项目合集。`experience.weeks` 负责周次和开放状态，`projects` 负责具体项目，项目详情页再从项目对象读取材料路径。

| 层级 | 页面职责 | 允许出现的入口 |
| --- | --- | --- |
| `experience/index.html` | 说明项目目的、时间、参加方式、项目构成、体验版与进阶版关系、目录和联系方式 | 环境准备可直接打开；项目和 Week 使用“项目预览”或“查看详情” |
| `experience/week-*.html` | 展示该周已登记项目、项目编号、体验/进阶关系和开放状态 | 先进入对应项目详情；未开放时显示锁定状态 |
| `experience/project-*.html` | 说明一个项目的研究问题、输入、输出、体验/进阶区别和材料组成 | 每个材料卡只保留一个“打开”按钮 |
| `experience/material.html` | 阅读教学、实践或参考答案材料；实践页提供下载和 Kaggle 入口，答案页展示代码与结果 | 根据材料类型显示对应动作，不把入口返回到项目页 |
| `experience/teaching/*.html` | 提前解释概念、数据、方法和结果阅读方式 | 返回项目详情 |
| `experience/practice/*.ipynb` | 让学生在 Kaggle 中复制并修改；题目版保留需要完成的位置 | 由实践阅读页和 Kaggle 入口使用 |
| `experience/answers/*.html` | 展示同一实践任务的参考代码、分析和已保存结果 | 由参考答案材料页使用，不提供无效的上一页/下一页 |

项目 00—05 是对外显示的项目编号，仓库为了保持既有地址使用 `project-01`—`project-06`。项目 00 只有体验材料，进阶材料从项目 01 开始。体验 03—05 的教学、实践、答案和结果资产与 A03—A05 的公开 Kaggle 入口保持对应；`site.js` 锁定 Week 3—5 与进阶导航。进阶 01—05 的完整材料和项目 06—09 的本地原型不进入公开网站数据、GitHub Pages 或其他云端。

体验版不要求提交报告。进阶版在开放后才说明方法设计、方法选择、验证方案和报告要求。体验项目页面的教学、实践和参考答案文字都要面向零基础读者，用直接的概念说明和任务说明，不写作者内部制作过程。

### 3.5 资源中心

`resources/index.html` 只负责展示三个同层级合集：专业解读、项目与活动资料、教学文档库。三个合集的卡片高度和信息密度应保持同一设计规则，内部内容过长时在卡片内部滚动，不用大块空白拉齐。

- 专业解读：专业介绍、专业答疑和历年去向表；东北大学生物医学工程（中外合办）的限定信息只写在需要限定的专业内容中，通用职业、科研和升学信息保持通用表达。
- 项目与活动资料：课程、活动和项目相关资料，名称使用完整项目名称；未开放或内部进阶材料不展示。
- 教学文档库：按开放状态和材料类型列出可阅读文档。体验项目的教学、实践和实践项目参考答案从项目数据生成，避免新增项目时忘记更新文档库。
- 科研基础环境准备：GitHub 保留 HTML；Notion 按要求使用原生标题、段落、列表和图片块。软件版本、平台操作和章节结构变化时分别检查两端。

## 4. 单一数据源和传播路径

下表描述“改哪里、会影响哪里”。页面模板只能负责渲染，除非是布局或上下文显示规则，否则不在 `site.js` 复制正文。

| 数据对象 | 唯一来源 | 传播位置 | 常见联动 |
| --- | --- | --- | --- |
| 团队定位 | `team.lead`、`team.paragraphs` | 首页首屏、团队介绍首屏和正文 | 团队身份或小标题变化时检查首页和团队页 |
| 成员数量与概况 | `team.facts` | 团队介绍统计和相关概览 | 数字变化时检查是否还有旧数字硬编码 |
| 负责人 | `team.leaders` | 首页负责人、团队页负责人、负责人子页面 | 姓名、年级、职务、简介、锚点和首页入口一起检查 |
| 毕业去向 | `team.destinationRecords`、`team.destinationUniversityOrder` | 成员高校、去向子页、团队概况 | 学位组、学校顺序和人数一起检查 |
| 在校高校 | `team.undergraduateNetwork`、`team.undergraduateNotes` | 成员高校三个入口 | 学校名称、横向排版和说明一起检查 |
| 成果统计与条目 | `team.achievementMetrics`、`team.achievementNote`、`team.achievements` | 首页、团队介绍、完整成果页、宣传文案 | 数字分类与详细条目必须保持一致 |
| 团队动态 | `team.news` | 首页滚动区、`team/news.html`、成果页和宣传文案 | 按日期倒序；新增条目放同一数据数组，不只改首页 |
| 活动 | `modules`、`team.activities` | 首页、项目与活动目录、活动详情页、团队活动页 | 标题、日期、受众、排序、详情页和课程目录一起检查 |
| 体验项目 | `experience`、`experience.weeks`、`projects` | 首页、项目目录、Week 页、项目详情、资料中心 | 编号、开放状态、体验/进阶关系、材料路径和预览规则一起检查 |
| 联系方式 | `experience.contact` | 首页和体验项目主页 | 二维码图片、标题、邮箱和显示上下文一起检查；不复制联系人数组 |
| 资源合集 | `resourceCollections` | 首页资源预览、资源中心、专业专题、教学文档库 | 合集标题、同层级副标题、排序、开放状态和链接一起检查 |

### 4.1 首页和体验项目联系方式的上下文

`experience.contact.channels` 中同一二维码只保存一个图片路径和一个默认标题。首页调用 `contactMarkup` 时传入 `context: "home"`，第二个群聊二维码使用 `homeTitle: "本科生科研入门体验项目专属群聊"`；体验项目主页不传该上下文，继续显示“本项目专属群聊二维码”。这样首页和项目页的名称符合各自语境，同时不会因为复制数据造成图片或邮箱不同步。

## 5. 教学、实践与实践项目参考答案的统一写法

三类材料是同一项目的三个阅读环节，不能各自发展成不同的叙述方式。项目对象中的 `teaching`/`experienceTeaching`、`practice`/`experiencePractice`、`answer`/`experienceAnswer` 分别指向这三类材料。

### 5.1 教学项目

- 先说明研究对象、数据形态、任务和结果，再介绍完成实践所需的概念、方法和结果阅读方式。
- 概念要用图像、矩阵、shape、简单例子或项目对应结果解释；抽象术语后面紧跟具体含义。
- 标题和段落使用自然、朴素的陈述，避免“闭环”“回到”“最小训练闭环”等模板化连接词，也不写作者与学生之间的对话。
- 体验项目不写提交报告、提交作业或报告考核要求；需要记录观察时，写成学生实际要完成的学习任务。
- 图片、编号、返回项目详情按钮和相对路径必须可用；项目 01—05 的进阶教学未开放前不发布。

### 5.2 实践项目

- 题目版与参考答案版使用相同的任务顺序、标题和注释；题目版只在需要学生完成的位置留出代码或文字任务。
- 面向零基础学生的 Markdown 要解释变量、输入输出、代码作用、填写依据和检查方式；需要修改的代码块前后用整行注释明确边界。
- 实践说明应告诉学生优先在 Kaggle 公开 Notebook 中“复制并编辑”到自己的账户后运行和修改，下载到电脑是补充方式；网页代码块用于阅读，实践要在 Notebook 中完成。
- 结果应出现在对应实践步骤之后，清楚区分输入、输出、真实图像、生成图像和评价指标；不在实践材料开头直接堆放结果。
- 实践项目的任务简介直接说明填写位置、确定依据和完成后的检查方式，不出现工具推荐、作者内部编排或制作过程。

### 5.3 实践项目参考答案

- 页面中使用真正的代码块，代码、Markdown 说明和输出结果按实践步骤排列；不要把代码直接放在普通文本段落中。
- 参考答案与题目版对应位置一致，补全同样的代码和文字任务，便于学生逐段核对。
- 展示实际保存的结果，包括图像、曲线、指标或分析文本；图像标题明确输入和输出的区别。
- 页面统一使用“实践项目参考答案”；说明“参考答案仅做参考，并非代表唯一正确结果，效果以运行结果为准，具体代码形式可自行调整”。
- 不设置无效的上一页/下一页按钮。Kaggle 标准答案入口只放在参考答案打开后的合理位置，不放回项目主页材料卡。

### 5.4 体验版与进阶版

| 项目层级 | 学生要做什么 | 公开状态 |
| --- | --- | --- |
| 体验版 | 阅读教学内容，补全实践中的指定代码或文字，查看自己的结果并用参考答案核对 | 按 Week 状态开放 |
| 进阶版 | 学习更深的方法，选择或设计方法，完成实践，解释方法选择和验证结果并撰写报告 | 当前锁定，材料保留本地内部归档 |

体验版与进阶版可以使用同一方向，但任务目标、难度、数据或方法可以不同；上层项目说明必须把差异写清楚，不能让学生把进阶项目误解为体验项目的直接答案。

### 5.5 后续项目 06—09 的本地原型

后续项目目前只保留在学生材料目录，不进入公开项目数据。每个教学页仍按公开教学页的阅读方式组织：正文先解释对象和结果边界，随后在相关章节放置一张项目结果图、一个数据或方法结构图，以及一个不依赖外部服务的参数交互。结果图来自该项目的本地结果目录；交互只展示参数变化的方向，并在页面上标明示意性质。题目 Notebook、参考答案和项目设计文件继续沿用同一项目编号，修改教学页时检查图像相对路径、交互控件 ID 和实践任务顺序。

## 6. 新增内容的可扩展方式

### 6.1 新增项目

1. 在 `projects` 登记唯一 `id`、公开编号、标题、Week、简述、输入、输出、状态和材料路径。
2. 在 `experience.weeks` 的项目列表中登记所属周次；已开放前保持 `open: false`，不要先生成可点击材料。
3. 按 `experience/teaching/`、`experience/practice/`、`experience/answers/` 放置体验材料；进阶材料进入本地内部归档，不混入公开路径。
4. 运行教学文档库生成逻辑，确认开放项目自动出现，未开放项目不出现。
5. 检查首页预览、项目总览、Week 页、项目详情和材料阅读页；不要修改“项目有多少个”之类的上层文案。

### 6.2 新增 Week 或课程

- 新 Week 只增加 `experience.weeks` 数据和对应页面包装文件，沿用现有锁定、项目预览和返回路径。
- 新课程在对应 `modules[*].lessons` 中登记标题、说明、日期、站内地址和外部入口。课程页的项目预览从课程数据生成，不在首页另抄一份。
- 山东大学课程的 Kaggle 实践入口放在对应课程子页面；复旦大学课程的授课标题和完成状态在课程数据中维护。

### 6.3 新增资源或教学文档

- 先确定它属于专业解读、项目与活动资料还是教学文档库，再登记合集条目；不为单篇文档新增顶部导航。
- 若文档属于某个项目，项目材料页和教学文档库引用同一实际文件或同一数据对象；需要不同上下文时增加显示字段，不复制正文。
- 新增 Notion 页面时先对应 GitHub 页面路径和职责，再处理公开权限和嵌入附件；两端内容结构应保持一致。

### 6.4 新增成员、成果、动态和联系方式

- 成员改动先更新成员数据，再检查首页、团队页、去向页、负责人页和相关宣传文件。
- 成果动态按日期倒序加入 `team.news`，同时更新统计卡或完整成果条目；首页不单独维护一套动态。
- 二维码只替换 `experience.contact` 的图片或标题字段；如首页和项目页需要不同称呼，用上下文标题字段解决。

## 7. 新需求的登记和联动流程

收到新需求后按以下顺序处理：

1. 归类为内容、交互/布局、实践材料、平台同步、部署/域名或维护流程。
2. 在 `docs/REQUIREMENTS-REGISTER.md` 中判断它是新增要求、对已有要求的替代，还是已有规则下的局部修改；冲突时以后提出的明确口径为准。
3. 在本文件定位上游数据、下游页面和材料关系，写清楚需要联动的范围；不受影响的页面不加入任务清单。
4. 先改唯一数据源或实际材料，再改必要的渲染/样式；只为显示上下文增加字段或参数，不复制内容。
5. 做与影响范围匹配的验证：文案改动做定位和内容回读，数据改动做语法和直接页面回读，布局改动做目标桌面/窄屏检查，材料改动检查编号、代码块、图片和对应入口，部署或云端同步才做对应外部回读。
6. 在状态文件记录本地、提交、远端、Pages、Notion 等不同状态；“已改文件”不等于“已推送”或“已公开回读”。
7. 若新需求改变页面关系、数据来源或材料规范，回到本文件更新相应章节；若只是一次性正文修正，只在要求登记表记录，不扩写架构规则。

## 9. 维护文件之间的分工

- `docs/REQUIREMENTS-REGISTER.md`：记录当前有效要求、被替代要求、待确认事项和变更登记。
- `docs/DESIGN-LINKAGE.md`：记录页面职责、设计关系、数据传播、材料规范和扩展方式。
- `SITE-MAINTENANCE.md`：记录逐页清单、平台对照、发布检查和具体维护操作。
- `docs/site-architecture.md`：记录总体信息架构和公开页面边界；若本文件与它描述同一关系，以本文件的联动细节和要求登记表的最新口径为准，并在发现差异时一起修正。
- `docs/experience-materials.md`：记录体验/进阶材料来源、编号映射、导入和材料级验收。
- `docs/environment-materials.md`：记录科研基础环境准备的 GitHub HTML、Notion 原生内容和图片维护方式。
- `_codex_state/current_task_state.md`：记录当前执行到哪一步、哪些文件已改、哪些已提交或推送；它不是长期设计文档。
